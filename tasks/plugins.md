# User plugins without a rebuild

*Plan only — nothing here is implemented yet.*

roBrowser already has a plugin system, and it is better suited to this than it
first looks. `Plugins/PluginManager.js` reads a `plugins` map from the client
config and dynamic-imports each entry:

```js
plugins: {
    KeyboardControl: 'KeyToMove_v1/KeyToMove',
    Minimap:         { path: 'BetterMinimap/index', pars: { scale: 2 } }
}
```

The important detail is the import itself:

```js
import(/* @vite-ignore */ resolvedPath)
```

`@vite-ignore` tells the bundler to leave that call alone, so the path is
resolved **at runtime, relative to the built module's URL** — not baked in at
build time. A file dropped next to `Online.js` on the asset server is
importable without rebuilding anything. That is the whole feature; the rest is
plumbing and guard rails.

---

## Shape

**A plugins directory the user owns**

```
~/Library/Application Support/com.ragnarokmac.app/plugins/
    my-plugin/
        plugin.json      # name, version, description, entry
        index.js         # default-exported function, returns true on success
```

Application Support rather than inside the `.app`: the bundle should stay
replaceable and, once it is signed, writing into it breaks the signature.

**Served by the asset server**

RemoteClient-JS already serves loose files ahead of the GRFs, so this is one
`express.static` mount at `/plugins`, or a `DATA_OVERRIDE_PATH`-style config
entry. Then `plugins: { MyPlugin: 'plugins/my-plugin/index' }` resolves.

One caveat to design around: the built client lives at `/Online.js`, so
`'./plugins/...'` resolves from the server root. That is fine, but it means the
path in config is server-relative and needs documenting, because it is the one
thing that will confuse people.

**Managed from Settings**

A Plugins pane that lists what it finds in that directory, with a checkbox
each. Enabled plugins are written into the `plugins` map in
`Config.local.js` — the file `scripts/link-assets.sh` already generates — and
take effect on the next client load. Buttons for *Open plugins folder* and
*Reload client* cover the whole authoring loop without a terminal.

---

## What needs care

- **Plugins are not sandboxed.** They are ES modules running in the same origin
  as the client, with access to the game's internals and the same-origin asset
  server. That is exactly what makes them useful, and it means installing one is
  equivalent to running arbitrary code. Settings should say so plainly, once,
  rather than pretending otherwise. Do not add a plugin *browser* that installs
  from a URL — a folder the user fills deliberately is a meaningfully different
  trust decision.
- **Failures must be visible.** PluginManager currently swallows load errors
  into `console.error`, which nobody sees in a Tauri window with no devtools.
  The manager should report failures somewhere the Settings pane can show, or
  plugins will fail silently and look like "the app is broken".
- **Version drift.** Plugins reach into internals with no stable API, so a
  roBrowser bump can break them. `plugin.json` should record which client
  version it was written against, and the pane should flag a mismatch instead
  of letting it fail obscurely.
- **Our own patches should migrate here.** WASD movement is currently a patch
  to `MapEngine.js` re-applied by `scripts/patch-client.sh`. PluginManager's own
  docstring uses `KeyToMove` as its example plugin, which is a strong hint this
  is the intended shape. Converting it would shrink the patch set to the two
  genuine upstream bug fixes and make our own feature the reference example of
  the plugin API.

## Open questions

- Do enabled plugins belong in `Config.local.js` (regenerated by
  `link-assets.sh`, so it would need to merge rather than overwrite) or in a
  separate `plugins.json` the page fetches? The latter is cleaner and avoids a
  generated file having hand-edited state in it.
- Should a plugin be able to ship assets (sprites, sounds)? If so the directory
  needs to be served wholesale, not just its JS.
- Is there value in shipping one or two first-party plugins as examples, or does
  that imply a support commitment we do not want?
